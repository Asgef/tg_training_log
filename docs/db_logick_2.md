# ТЗ: База данных v2 для журнала тренировок

## 1) Цель

Обеспечить хранение тренировочных данных так, чтобы система могла формировать **стабильный датасет нагрузки на мышцы/зоны** во времени (для графиков и ML), при этом поддерживая пользовательские “тренажёры/упражнения” и ведение подходов **только внутри тренировки (сессии)**.

---

## 2) Ключевая концепция данных

### 2.1 Два уровня абстракции справочника

Справочник тела состоит из:

* **Мышечные зоны** (`muscle_zones`) — термины бодибилдинга на русском.
* **Мышцы** (`muscles`) — конкретные мышцы на русском.

Между зонами и мышцами существует связь:

* **многие-ко-многим** (`muscle_zone_muscles`), т.к. одна мышца может входить в несколько зон, и одна зона содержит несколько мышц.

### 2.2 Тренажёр/упражнение пользователя

Пользователь создаёт `machines` (включая упражнения, если пользователь так называет. Тренажёр или упражнение, это одна и таже сущьность).
У каждого `machine` может быть назначено:

* 0..N **зон** (`machine_zones`)
* 0..N **мышц** (`machine_muscles`)

Назначение зон — быстрый UX, назначение мышц — точность.

### 2.3 Тренировка как контейнер

Любые подходы записываются **только внутри активной тренировки**:

* `workout_sessions` создаётся при “Начать тренировку”
* закрывается при “Завершить тренировку”
* может быть отменена (см. UI-уже реализован)

### 2.4 Подход как событие

`set_entries` — факт выполнения подхода:

* ссылка на сессию (`session_id`)
* ссылка на тренажёр/упражнение (`machine_id`)
* значения нагрузки (вес/повторы/отказ)
* время фиксации (`created_at`)

### 2.5 Snapshot на момент подхода (обязательное требование)

Система обязана фиксировать “как было тогда”, чтобы история не менялась, если пользователь позже отредактировал `machine`.

При создании `set_entries` должны фиксироваться снимки:

* `set_entry_zones` — зоны, релевантные этому подходу
* `set_entry_muscles` — мышцы, релевантные этому подходу

Таким образом:

* `machine_*` = актуальная разметка “сейчас”
* `set_entry_*` = исторический снимок “тогда”

## 3) Требования к целостности данных

### 3.1 Пользователь

* `telegram_id` уникален.
* `is_registered` управляет доступом к функционалу (логика бота вне БД, но поле хранится здесь).

### 3.2 Справочники

* Названия `muscle_zones.name` и `muscles.name` уникальны.
* В `muscle_zone_muscles` запрещены дубликаты связей.

### 3.3 Machines

* Принадлежат пользователю (`user_id`).
* Поддерживается `is_archived`, архивные записи не удаляются физически. Можно создать тренажёр с таким же именем тренажёра в архиве. Нельзя создать тренажёр с именем существующего активного тренажёра.

### 3.4 Sessions

* Одна активная сессия на пользователя (ended_at = null) в рамках бизнес-логики приложения.

### 3.5 Set Entries

* Каждый подход обязан ссылаться на `workout_sessions` и `machines`.
* `weight` > 0, `reps` > 0.
* `is_failure` boolean.

### 3.6 Snapshot

* Для каждого созданного `set_entries` система должна создать связанные записи snapshot:

  * `set_entry_zones`: 0..N строк
  * `set_entry_muscles`: 0..N строк
* Snapshot должен соответствовать разметке тренажёра **на момент записи**.

---

## 4) Логика приложения, которую должна обеспечивать БД (и к которой приводим текущую систему)

### 4.1 Управление тренировкой

Приложение должно использовать `workout_sessions` как источник состояния:

* “Начать тренировку” → создать новую сессию
* “Завершить тренировку” → выставить ended_at
* “Отменить тренировку” → удалить/аннулировать сессию (реализовано в UI) и связанные подходы

### 4.2 Запись подхода

При записи подхода приложение обязано:

1. определить текущую активную сессию
2. создать `set_entries` с параметрами подхода
3. зафиксировать snapshot зон и мышц в `set_entry_zones` и `set_entry_muscles`

### 4.3 Управление тренажёрами

Приложение должно поддерживать:

* создание/редактирование `machines`
* назначение зон (`machine_zones`)
* назначение мышц (`machine_muscles`)
* просмотр характеристик тренажёра (в UI)

### 4.4 Совместимость с существующим кодом

* Таблица `machines` сохраняется с этим названием.
* Остальные сущности и связи приводятся к новой схеме v2.
* Таблица `processed_updates` сохраняется без изменений.

## 6) Поля метаданных

Все бизнес-таблицы (кроме `processed_updates`) должны содержать:

* `created_at timestamptz`
* `updated_at timestamptz`

В `processed_updates`:

* `processed_at timestamptz` (как есть)

---

## 7) Критерии готовности (DoD)

Считается выполненным, если:

* новая схема БД присутствует и применена;
* запись подходов возможна только при активной тренировке;
* при каждом новом подходе создаются snapshot-записи зон и мышц;
* редактирование тренажёра не меняет историю существующих подходов (snapshot не меняется);
* существующие данные перенесены без потерь;
* `processed_updates` сохранена.
