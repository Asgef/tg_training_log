# Техническое задание: Telegram-бот “Журнал тренировок”

## 0) Назначение документа

Документ описывает требования к Telegram-боту для ведения журнала силовых тренировок: управление тренажёрами, запись подходов в рамках тренировочных сессий, хранение данных в PostgreSQL и экспорт в Google Sheets через сервисный аккаунт.

---

## 1) Цели и ценность продукта

### 1.1 Цели

* Дать пользователю максимально быстрый способ фиксировать подходы: тренажёр → вес/повторы/RIR → сохранить.
* Позволить пользователю вести собственный справочник тренажёров (имя, фото, мышцы).
* Вести тренировки как сущность (начать/закончить) и привязывать подходы к тренировке.
* Экспортировать данные в Google Sheets в формате, пригодном для графиков/аналитики/обработки.

### 1.2 Не-цели (сознательно не делаем в MVP)

* Сложные планы тренировок/программы/циклирование/проценты 1ПМ.
* Социальные функции, лидерборды.
* Поддержка нескольких языков интерфейса.
* Хранение фото в S3/MinIO (на старте используем Telegram file_id).

---

## 2) Роли и доступ

### 2.1 Роли

* **User** — конечный пользователь бота.
* **Admin** — администратор, который подтверждает регистрацию пользователей.

### 2.2 Модель доступа (бот “закрытый”)

* По умолчанию пользователь не имеет доступа к функционалу.
* На /start пользователь видит предложение “Зарегистрироваться”.
* После запроса регистрации администратор подтверждает/отклоняет запрос через интерфейс бота (inline-кнопки).
* После подтверждения пользователь получает доступ ко всем функциям.

---

## 3) Основные сущности и данные

### 3.1 User

Хранит данные Telegram и настройки экспорта.

* `id` (PK)
* `telegram_id` (unique)
* `telegram_username` (nullable)
* `first_name` (nullable)
* `is_registered` (bool)
* `google_sheet_url` (nullable)
* `google_spreadsheet_id` (nullable)
* `google_sheet_connected_at` (nullable)
* `created_at`, `updated_at`

### 3.2 MuscleGroup (опционально, но рекомендовано сразу)

Справочник крупных групп мышц для удобства UI/навигации.

* `id` (PK)
* `name` (unique) — напр. “Грудь”, “Спина”, “Ноги”, “Плечи”, “Руки”, “Пресс”

### 3.3 Muscle

Справочник анатомически точных мышц.

* `id` (PK)
* `name` (unique) — напр. “Большая грудная мышца”, “Бицепс плеча”
* `group_id` (nullable FK -> MuscleGroup)

### 3.4 Machine

Тренажёр создаётся **индивидуально для пользователя**.

* `id` (PK)
* `user_id` (FK -> User)
* `name`
* `photo_file_id` (nullable) — Telegram file_id
* `photo_unique_id` (nullable) — Telegram file_unique_id (если нужно)
* `is_archived` (bool, default false)
* `created_at`, `updated_at`

### 3.5 MachineMuscle (M:N)

* `machine_id` (FK -> Machine)
* `muscle_id` (FK -> Muscle)
* unique(machine_id, muscle_id)

### 3.6 WorkoutSession

Тренировочная сессия.

* `id` (PK)
* `user_id` (FK -> User)
* `started_at` (timestamptz)
* `ended_at` (nullable timestamptz)
* `note` (nullable text)

### 3.7 SetEntry (подход)

Журнал подходов.

* `id` (PK)
* `user_id` (FK -> User)
* `machine_id` (FK -> Machine)
* `session_id` (nullable FK -> WorkoutSession) — но в обычном сценарии при активной тренировке заполнен
* `weight` (numeric) — поддержка 2.5
* `reps` (int)
* `rir` (int, 0..5)
* `performed_at` (timestamptz)

### 3.8 Временные зоны

* В БД хранить время как `timestamptz` (UTC).
* В UI показывать пользователю локальное время (настройка по умолчанию: Europe/Berlin).

## 4) Пользовательские сценарии (User Stories)

### 4.1 Регистрация

* Пользователь нажимает “Зарегистрироваться”.
* Вводит короткое описание “кто я”.
* Админ получает карточку с данными и кнопками Approve/Reject.
* При Approve: `is_registered=true`, бот уведомляет пользователя.
* При Reject: бот уведомляет пользователя (нейтрально).

### 4.2 Управление тренировкой (сессией)

* Пользователь нажимает “Начать тренировку”.
* Создаётся `WorkoutSession` со `started_at=now`, `ended_at=null`.
* Пользователь нажимает “Закончить тренировку”.
* У текущей активной сессии выставляется `ended_at=now`.

Правила:

* У пользователя может быть не более одной активной сессии (ended_at is null).
* Если активной сессии нет — кнопка “Закончить” недоступна/не показывается.

### 4.3 Добавление тренажёра

* Пользователь выбирает “Тренажёры” → “Добавить”.
* Вводит:

  * имя тренажёра
  * фото (опционально)
  * выбирает мышцы (чекбоксы), опционально с группировкой по MuscleGroup
* Нажимает “Сохранить” → создаётся Machine + связи MachineMuscle.

### 4.4 Просмотр характеристик тренажёра

* Из списка тренажёров пользователь открывает карточку:

  * фото (если есть)
  * список мышц
* Из карточки доступно:

  * “Записать подход”
  * “Редактировать”
  * “Архивировать/Разархивировать”

### 4.5 Запись подхода

* Пользователь выбирает “Записать подход”.
* Выбирает тренажёр.
* Бот показывает:

  * краткие характеристики (мышцы)
  * “Последний подход на этом тренажёре” (если существует)
* Пользователь вводит:

  * вес (numeric)
  * повторы (int)
  * RIR (0..5)
* Нажимает “Сохранить”.
* Создаётся SetEntry с `performed_at=now`.
* Если есть активная WorkoutSession → `session_id` заполняется.

UX-ускорители:

* Кнопка “Повторить прошлый подход” (подставляет вес/повторы/RIR с возможностью правки).
* Быстрые кнопки изменения веса (+2.5, +5) и частых повторов (6/8/10/12) — допустимо как улучшение, но не блокирует MVP.

### 4.6 Редактирование/удаление подхода

* Пользователь может найти последний подход и исправить значения.
* Удаление предпочтительно “мягкое” (например, `is_deleted`), но можно начать с физического удаления, если экспорт не требует синхронизации удалений.
* Если экспорт в Google Sheets реализован инкрементально, редактирование/удаление должно учитывать стратегию обновления.

## 5) Экспорт в Google Sheets

### 5.1 Авторизация

* Используется **Google Service Account**.
* Пользователь подключает таблицу, предоставляя ссылку на Google Spreadsheet.
* При отсутствии прав бот сообщает сервисный email и просит дать доступ **Editor**.

### 5.2 Хранение подключения

* При успешной проверке сохраняются:

  * `google_sheet_url`
  * `google_spreadsheet_id`
  * `google_sheet_connected_at`

### 5.3 Структура Spreadsheet

Два листа:

1. **Machines**
2. **Log**

Если листов нет — бот создаёт их.
Если есть — использует существующие.

### 5.4 Формат листа Machines (без фото)

Таблица (рекомендуемые колонки):

* `machine_id` (строка/число)
* `name`
* `muscles` (строка: перечисление через запятую)
* `updated_at` (ISO)

Правило выгрузки: **upsert** по `machine_id` (обновлять изменённые).

### 5.5 Формат листа Log (журнал подходов)

Рекомендуемые колонки:

* `set_id`
* `performed_at` (ISO)
* `date` (YYYY-MM-DD, для pivot)
* `time` (HH:MM:SS)
* `session_id` (nullable)
* `machine_id`
* `machine_name` (денормализация для удобства)
* `weight`
* `reps`
* `rir`

Правило выгрузки: **append** новых строк, чтобы не перезаписывать всю историю.

### 5.6 Инкрементальная выгрузка

* Система хранит маркер последней успешной выгрузки:

  * вариант A: `last_exported_set_id` (по монотонному ID)
  * вариант B: `last_exported_at` + сортировка/фильтрация
* При экспорте в Log отправляются только записи новее маркера.

### 5.7 Обработка ошибок

* Если нет прав записи: бот сообщает “нет доступа” и инструкцию “дать Editor сервисному email”.
* Если ссылка невалидна / spreadsheet_id не извлечён: бот просит корректную ссылку.
* Любая ошибка API логируется на сервере; пользователю выдаётся короткое сообщение + рекомендация.

## 6) Интерфейс бота (меню и навигация)

### 6.1 /start

Если `is_registered=false`:

* приветствие
* кнопка “Зарегистрироваться”

Если `is_registered=true`:

* показать главное меню

### 6.2 Главное меню (registered)

* ▶️ Начать тренировку (если нет активной)
* ⏹ Закончить тренировку (если есть активная)
* ➕ Записать подход
* 🏋️ Тренажёры
* 🔗 Подключить Google Sheets
* 📤 Выгрузить данные
* ⚙️ Настройки (минимум: показать статус таблицы)

### 6.3 Ограничения Telegram UI

* Выбор мышц реализовать через “чекбоксы” (inline buttons с toggling и кнопкой “Сохранить”).
* Списки тренажёров: пагинация или “последние/поиск” при росте.
* Во всех вводах чисел — валидация и понятные ошибки.

## 7) Валидация данных

### 7.1 SetEntry

* `weight` > 0 (numeric, допускаются десятичные)
* `reps` > 0 (int)
* `rir` int (0..5)
* `machine_id` принадлежит пользователю

### 7.2 Machine

* `name` не пустой
* мышцы могут быть пустыми (допускается, но не рекомендуется) — решение: либо разрешить, либо требовать минимум 1 мышцу (предпочтительно требовать 1).

## 10) Нефункциональные требования

* Надёжность: бот должен корректно переживать перезапуск контейнера.
* Идемпотентность: повторные нажатия на inline-кнопки не должны ломать состояние (особенно toggles).
* Производительность: операции записи подхода < 1 сек.
* Безопасность: токены/ключи не в репозитории; сервис-аккаунт имеет минимальные права; доступ к таблице регулирует пользователь.
* Аудит: логировать важные действия (регистрация, экспорт, ошибки Google API).

## 11) MVP-объём работ (Definition of Done)

### MVP включает

1. Закрытый доступ + админ approve/reject внутри бота.
2. WorkoutSession: начать/закончить, хранение активной сессии.
3. CRUD тренажёров: создать, просмотреть, редактировать, архивировать.
4. Запись подхода: вес/повторы/RIR, привязка к активной сессии.
5. “Последний подход” и “повторить прошлый” (как минимум для последнего подхода) — допускается как v1, но рекомендовано.
6. Подключение Google Sheets через сервис-аккаунт.
7. Экспорт:

   * Machines (upsert)
   * Log (append инкрементально)
8. Базовая обработка ошибок и пользовательские сообщения.

### Не входит в MVP (можно v1/v2)

* Поиск по тренажёрам (если список небольшой — позже)
* Умная аналитика/графики прямо в боте
* Синхронизация удалений/редактирования в Google Sheets (можно ограничиться тем, что экспорт — append; редактирование в БД не “чинит” старые строки в Sheets)

## 12) Открытые решения (фиксируем заранее, чтобы Spec Kit не гадал)

* Стратегия редактирования/удаления и отражения изменений в Google Sheets:

  * MVP: экспорт в Log только append; правки в БД не редактируют старые строки в Sheets.
  * Альтернатива v2: обновлять строку по `set_id` (поиск строки и update) — сложнее, но консистентно.
* Требование “минимум 1 мышца на тренажёр”:

  * Рекомендуется: да (иначе характеристик нет).
